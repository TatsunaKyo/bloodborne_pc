The owner's R49 capture does not establish a traversal fix. Its largest later hitch is submission 1600 at 34.108 s: 41.656 ms real interval, 16.46 ms guest submission interval, 41.31 ms GPU-thread flip interval and 28.528 ms submit-to-flip delay. Final presentation/SDK CPU time is about 0.10 ms. The archive and separately supplied log agree on these performance records; the archive redacts private paths.

In that window the draw-recording thread has 1545 draw spans totaling 17.501 ms. The copy thread has 1788 recorded host copies totaling 14.822 ms. The protection worker has 537 native protection spans totaling 9.468 ms. Protection dependencies overlap GPU decode (231 calls, 8.851 ms), Vulkan recording (184 calls, 7.851 ms) and host copies (28 calls, 3.533 ms). ## Resource-scoped protection completion

R49's `CopySparseMemory` and image-hash checks drain the global issued protection prefix. Reading an already protected range A can therefore wait behind unrelated range B. R50 captures a range and sequence prefix under the queue mutex, examines pending and active requests, and waits only for overlapping requests from that prefix. Each completed native call marks its constituent requests installed and can retire a reader before other calls from the same worker batch finish. A later request at the same address does not extend the captured prefix. A sealed boundary prevents merging a pending prefix with later requests.

The C runtime narrows a dependency only for readable, direct guest mappings without overlapping physical aliases. It holds its VMA read lock throughout eligibility and the wait, preventing a concurrent mapping change from invalidating that decision. Flexible memory, aliases, inaccessible/reserved spans, holes, overflow and a missing range hook retain a full drain. Mapping changes, access grants, no-access transitions and existing current-image watches retain their earlier ordering. The native worker still acquires no VMA, tracker or GPU locks, so callers may wait while holding those locks. This does not replace the dirty masks or allow a snapshot before its own write watch is installed.

## Capture the copy epoch when the guest requests a fence

R49 registers `AfterCopies` only when the recorded command executes. Copies queued after the guest's fence request can join that dependency in the meantime. R50 registers the asynchronous copy prefix immediately at the request and joins it with the recorder prefix using two completion arrivals. Inline recorded copies are covered by recorder order; asynchronous copies are covered by the copy pool's FIFO epoch callbacks. Both must arrive before the guest signal and completion count. No worker blocks waiting for the other arrival, and no unrelated global watch ticket is added: each snapshot already waits for its own installation.

`WaitHostCopies` still waits for recorded and asynchronous host copies. It no longer drains protection requests unrelated to those copies. The protected-memory and scheduler fixtures verify relevant waits, completion counters, copied contents and subsequent guest writes. This is an ordering change, not a change to the target FPS, game simulation timing or the NVIDIA cap implementation.

## Avoid allocating command storage while holding the recorder mutex

`AcquireChunk` now removes a reusable chunk under the mutex, then allocates outside it if none exists. `make_unique_for_overwrite<RecordChunk>` initializes the class's explicit bookkeeping defaults without zero-filling unused 128 KiB command storage. Commands are still constructed before execution and recycled chunks still reset their used count and linked list. The R49/current allocator control deliberately holds heap allocation and checks whether the recorder can return a spare chunk. It demonstrates the lock scope, not a measured gameplay speedup.

## Bounded causal evidence in traversal captures

The optional CPU flight recorder adds request IDs, dependency edges, installed-request events, native thread IDs, resource spans and shader/pipeline keys. `BB_HITCH_TRACE_PATH` enables a JSONL writer with a 16 MiB cap, at most 16384 selected events per hitch window and two pending windows. Serialization and file writes occur on a background-priority thread. Normal launches do not enable this file. The launcher enables it for the existing traversal/NVIDIA diagnostics and includes the filtered file in the same diagnostic ZIP, without requiring F8. A steady-clock/QPC anchor, PID and module base allow external correlation; the trace is explicitly window-limited.

The exporter filters field names, numeric ranges, labels and address syntax, rejects linked/oversized files, retains complete records after an interrupted tail, records truncation/drop conditions and includes the data in existing CRC/SHA256 checks. It stores addresses and metadata, not resource contents. This is not a sampled CPU profile, context-switch trace or measurement of individual displayed frames. It can show which captured request a snapshot awaited; an earlier queue event outside the selected window can still be absent. Nested spans and repeated operation bytes must not be summed as independent work.

## Controls and limits

The production C VMA implementation, protection queue, page/region trackers and snapshot method are exercised with real protected Linux mappings, including stores before installation, faults after snapshots, remapping/grants, an unrelated held request, a physical-alias fallback and 2000 write/upload cycles. Windows dispatcher bodies are separately exercised with recorded WinAPI boundaries. Queue controls cover backpressure, 6000 jobs/eight waiters, same-native-batch completion, 16 overlapping readers and later same-address work.

The actual copy pool and extracted production scheduler bodies demonstrate the R49 late-epoch error and R50's exclusion of held future copies. Sixty-four fences with alternating async/recorder arrival order check FIFO guest labels and copied values. The actual chunk class and old/current allocation bodies reproduce the old lock contention and verify the new bookkeeping. The production timeline writer is executed and its chronology, request links, native IDs, default-off behavior, file limit and archive privacy/integrity are checked. Relevant fixtures are also run with ASan/UBSan. These tests use recording backends for Vulkan and do not execute NVIDIA's SDK or the game.

No new renderer API, motion reconstruction formula, NVIDIA feature DLL, Encore NR support, FPS-counter smoothing or hidden frame cap is introduced. Existing original RTX 40/50 operation, opt-in RTX 20/30 provider gating and both required matching DLSS SR search paths are retained. Cemetery traversal, actual output-frame spacing, the stairs halo and transient geometry remain unverified on the target Windows/NVIDIA system. Do not publish these local controls as proof those gameplay defects are resolved.
