# R50 capture: first-use buffer volume, not a confirmed traversal fix

The owner supplied `session(10).json`, `session(10).log`, `Traversal-diagnostic(4).zip` and the separate `cpu-timeline.jsonl`. The diagnostic archive passes CRC and its per-file SHA256 manifest. Source commit/tree and the four executable hashes match R50. The session is 29.649 seconds on an RTX 5070 Ti, DLSS L at 1920x1080 to 3840x2160, original NVIDIA FG x2 with a 120 output cap and Reflex on. This is a short reproduction, not an equal-duration A/B performance benchmark.

## What remains in the capture

At 24.421 seconds, submission 936 has a 34.38 ms real interval, 17.06 ms guest submission interval, 34.03 ms GPU-thread flip interval and 21.33 ms submit-to-flip delay. Preparation is 0.24 ms; final presentation/SDK state is 0.11 ms. The delay in this event occurs before final presentation. A separate earlier 57.99 ms interval includes a 41.41 ms present/SDK call; these must not be conflated.

The before-flip window contains 1514 draw-record spans totaling 19.530 ms, 468 native protection spans totaling 10.999 ms, 1763 recorder host copies totaling 9.089 ms, 1536 resource-binding spans totaling 8.896 ms and 1501 vertex-preparation spans totaling 4.493 ms. The buffer-upload record reports 205447168 bytes across 310 batches (about 196 MiB of whole operations). Native protection spans cover 284221440 bytes of whole operations. These spans overlap and cannot be added together. Resource operation bytes are not disk traffic or a count of unique content.

The separate timeline retains 61 new 4 MiB tracker-region creation events in this window. It contains 703 queue/installation pairs and 125 source-range snapshot dependencies. For those retained dependencies, installation-to-waiter-resume median is 5.9 microseconds and maximum 20.9 microseconds. Queued-to-installed request latency has median 65 microseconds and maximum 592.6 microseconds. These are observations of retained events, not guarantees about omitted events. The range waits are associated with their own installation; merely widening concurrency again would not remove the first-use volume.

The trace also retains four shader-module compilation spans totaling 4.231 ms, two each for shader IDs 0x8aba0ecd and 0xd4b5fbf2. Shader identity alone does not identify the specialization. This does not demonstrate shader-cache corruption or establish that all those variants were already cached. Clearing the owner's cache is not a remedy supported by this capture.

The flight recorder reports an overwritten window prefix and the native timeline's selected window is capped at 16384 events. It is partial evidence. CPU tracing itself adds overhead; these timings must not be presented as an uninstrumented game benchmark. No captured image was requested, so this session cannot validate the stairs halo or transient geometry. The SDK's near-120 FPS samples do not reconstruct individual displayed-frame timestamps.

## An export defect found and fixed

The separate native timeline contains 17295 selected events across six windows. The diagnostic ZIP actually retains only 295, although its summary reports 17295: the generic support-report redactor caps every list at 100. R51 keeps the timeline's own strict event/file limits and redacts each whitelisted event separately. The same supplied file now retains all 17295 validated events, with its truncation status preserved. The regression checks an event list longer than 100 and counts the events actually serialized. The owner supplying the separate file made this analysis possible; another identical log-only request would not recover the discarded events.

## R51 changes the requested work

`ResolveVertexBuffers` previously asks `ObtainBuffer` to synchronize the whole V# descriptor, before binding it. Descriptor bounds are not the same as a direct draw's vertex footprint. A draw using a small subset of a shared vertex allocation can therefore trigger first-use protection, residency and upload of the whole descriptor.

R51 derives per-vertex byte demands from direct-draw vertex IDs and merges overlapping demands. It retains the original VkBuffer binding base, byte offsets, descriptor sizes, vertex IDs and draw parameters. A new cache path keeps a VkBuffer spanning the original descriptor, but establishes sparse residency and synchronizes only the proven read ranges. Existing 16/64 KiB residency/upload granularity remains. The unused pages remain CPU-dirty for later draws. GPU-authored bytes retain their existing tracking and readback policy.

For indexed draws, the optimization is deliberately limited to CPU-readable, unaliased indices already eligible for the existing small per-draw stream path (at most 16 KiB). One owned snapshot supplies both the scanned indices and the bound GPU stream. A later guest write cannot change the footprint without changing the bound version. Large cached index buffers are not turned into repeated stream uploads. GPU-authored/unsafe/unknown indices, custom restart values and missing fetch metadata use the existing path. Indirect draws retain their original path. Per-instance streams retain their full footprint, including divisor semantics. Attribute ends are conservatively overestimated using the maximum 32-byte core vertex format size plus the declared offset.

This is a reduction of requested input work, rather than moving the same full upload to another waiting thread. It does not prove the owner's measured 196 MiB were all avoidable, nor that a particular fraction will disappear in that route: the R50 trace did not label each upload by binding purpose or capture the needed index contents.

## Verification and practical limits

The production cache method and synchronization/region/page trackers are executed against real protected mappings. A 4 MiB descriptor with 6000 demanded bytes uploads 4194304 bytes through the prior full-binding path and 65536 bytes through the demanded-range path. The fetched bytes match; untouched pages remain dirty and nonresident, later ranges and subsequent writes upload correctly, invalid demands fall back and GPU-authored data survives. This is a controlled byte-count result, not a 64x gameplay speedup.

Production index-snapshot selection is executed for 16/32-bit indices, signed base vertices, restart, nonindexed draws and every fallback. Thirty thousand byte-coverage cases verify that referenced bytes remain covered. Production demand-merging/binding code checks interleaved streams, nonsequential attribute binding IDs, prepared/plain paths, full instance streams, original offsets/sizes and every fetched vertex byte. Relevant fixtures also run under ASan/UBSan. Existing descriptor-reuse, DMA ordering, protected upload and texture-helper controls remain required.

The cemetery, output pacing and image artifacts remain target-game validation items. No NVIDIA feature DLL, cap, FPS counter or motion-reconstruction formula is changed. The index snapshot is also used by the existing topology check so its CPU view matches the bound index stream. A change of graphics API is not justified by a CPU input-preparation spike. A possible Windows dirty-page backend would require a separate memory-mapping design: [GetWriteWatch](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-getwritewatch) requires VirtualAlloc/MEM_WRITE_WATCH allocations, while this runtime uses shared MapViewOfFile3 views and physical aliases. It is not a replacement function for the current mapped-view protection calls.
